# VoxtaBridge HTTP API

The game mod's HTTP listener (dedicated server, default port **30016**). The Voxta module is the only intended client;
this is the reference for developers. Every endpoint except `/ping` needs `Authorization: Bearer <token>` (the token
from `VoxtaBridge.cfg`). `player` is a SteamID64; without it the only player online is used.

## Endpoints

| Endpoint | Auth | Returns |
|---|---|---|
| `GET /ping` | none | mod, version, process mode, uptime `gameTimeS`: game time in seconds as dialogues see it (`GetGameTimeInSec()` = GameTicks / 20; stands still while the server is down). |
| `GET /status` | `Authorization: Bearer <token>` | players (ModApi v2 + API1 `Player_Info`), latest snapshot per loaded playfield (players, current structure incl. tanks/shield, `dockedTo` (name, if docked), `landed` (any landing gear extended; absent when unknown or on unverified game builds), per player `newStructures` (own or faction ships/bases created in the last minute: `id`, `name`, `type`, `kind` = `blueprint` or `starter`, `blueprint`; found by diffing snapshots, created between them per global.db), entity counts by type) Mining contracts: contract tokens in the player inventory carry `contract` (`faction`, `credits`, `reputation`, `wants`); `contractOffers` per SteamID lists the refinery offer rows (`key`, `value` = next time a contract is offered, `where`), whose value changes with every contract given. `gameTimeS` (as in `/ping`) to compare with the `contractOffers` values. `siteJobs` per SteamID: delivery jobs of the POIs on the player's playfield (Dialogues.ecf `…_Check` with a fixed `HandleQuestItemDrop` list, linked by prefab): `key` (POI id), `poi`, `where`, `needs` [{`item`, `name`, `count`}], `container`, `credits`, `choice`, `rep` (minimum standing), `done`. |
| `GET /debug/loadpf/<name>` | token | asks the server to load a playfield for 120 s (API1 `Request_Load_Playfield`), to test without a player |
| `POST /transfer` | token | form body `item`, `amount` (number or `all`), `to`, optional `from`, `player` (SteamID64; optional if one player is online). Moves items between containers of the structure the player is in and its docked vessels. While the player is inside a quest POI (a structure the game reports them in that isn't theirs), its hand-in containers count too: those named like a quest dialogue's `HandleQuestItemDrop('…')` container in Dialogues.ecf (RE2: `CargoDrop`, `MissionContainer`, `QuestContainer`); the same scope applies to `/find`, `/containers` and `/mining-contracts` `mine=1`. Answers `{"ok":…,"moved":…,"from":[…],"note":…}` or `{"ok":false,"error":…}`; every call is written to `VoxtaBridge.audit.log` |
| `POST /find` | token | form body `item` (name or part), optional `player`: where an item is (player bag/toolbar + every container in reach), totals per item, weapon state; logs a timing line per search Tokens (all the item `Token`) are told apart by their token id: each kind is its own entry, named from the token list (`name` "Mining Contract: Cobalt", `tokenId`), and found by that name; `/transfer` takes the same names and then moves only stacks of that token id. |
| `POST /items` | token | form body `query`: search the game's item list (config files, no player needed): exact names, craftable + constructors, weapon → ammo, ammo → weapons (player-facing, scenario-defined only); > 5 matches → names only |
| `POST /craft` | token | form body `item`, `amount`, `vc` (suffix, default `VC`), `confirm` (0 = plan only, 1 = craft), optional `player`: virtual crafting from the one container whose name ends with the suffix (docking group); recipes from Templates.ecf incl. intermediates; results + leftovers back into it; `RequireConstructor` (cfg, default false) checks constructor blocks on the ship |
| `POST /containers` | token | form body `structure` (name), optional `player`: containers of one structure in the player's transfer scope |
| `POST /where-to-buy` | token | form body `item`, optional `player` (and `at=<playfield>` for tests without a player): traders selling the item, their POIs and where those spawn (scenario TraderNPCConfig/Factions/DefReputation, playfield yamls, prefabs), the player's known sellers (visited POIs + trades) with LY, closest stars likely to have one (star class + territory only); places of factions below Neutral for the player's faction (save `game.dat`) are left out (listed as `hidden`); `knownPlanets`: bodies of discovered systems whose planet type (scenario playfields with that `PlanetType`) can spawn a matching trader POI, chance from spawn configs and territory, closest first; known sellers carry `tradesLocked` (unlock mission / work order) or `tradesUnlocked` when the factory's trades need a mission first (locked ones rank as 10 LY further), static POIs `tradeMission` |
| `POST /pois` | token | form body `scope` (`nearby` = 10 km, default, or `all`), optional `player`: POIs on the player's playfield that the player or their faction discovered, or that are loaded within 2 km, classified (trading / major faction base / small faction outpost / abandoned dungeon / wreck-salvage / civilian; resources counted, decoration left out), same-faction buildings within 600 m grouped into complexes with summed turrets (`cpgTurret`), faction and standing tier, distance; closest 10 groups; `yourStructures`: own/faction root structures (not docked, not the one the player is in) within 2 km |
| `POST /devices` | token | form body `action` (default `list`), optional `structure` (own structure in reach: the active structure's docking group and own structures within transfer range with theirs; default the active structure, like the item endpoints; answers carry `workingFrom`), optional `player`. `list`: power (on, use, capacity), shield (`active`, `level`, `capacity`, `rechargePerSecond`, `state`), tanks, signals (`panel`/`block`, on), named devices and groups (block type, on/off/mixed), LCDs (name, text), teleporters (target), light count. `find` `query` [`structure`]: signals and named devices or groups whose name or block type contains the query, plus `power` and `shield`, with state, at most 15 (`matches` = total); without `structure` the active structure and its docking group; never the full list. `states` `names` [`structure`]: on/off of the named signals and devices/groups only (`;`-separated, at most 50; unknown = `missing`), for the Voxta module's watches, cheap enough to poll. `control` `changes` [`structure`] (a write): `target=state` items separated by `;` (state on/off/toggle; target `power`, `shield`, a signal or a named device/group; prefix `signal:` / `device:` on a name clash), at most 20; per item `ok`, `result`, `before`/`now`, and for unknown names up to 8 `closeMatches`. Writes (own structures only, `DeviceControlEnabled`): `signal` `name` `state`=on/off/toggle (any control-panel or block signal, the game's own signal logic: receivers run, `SignalChanged` fires); `device` `name` `state` (every block of a named device or group); `power` `state` (main power, like the control panel); `shield` `state` (the shield generators; the shield warms up after switching on); `lcd` `name` [`text`] (read, or replace the text, max 2000 characters); `teleporter` `name` [`target`, `targetPlayfield`, `targetSystem`] (read; setting needs `DevWriteTools=true` because it ignores the game's range and reputation rules); `tank` `tank`=fuel/oxygen/pentaxid, `direction`=fill/drain, optional `item`, `amount` (items, default as many as fit), `container` (only this container, matched like `/transfer`): fill from the containers of the structure's docking group (items the scenario's tank blocks accept, FuelValue / O2Value per item, 1 per Pentaxid crystal; without `item` the smallest-value item on board), or drain into the item the game withdraws (first item of the tank blocks' accept list, e.g. Energy Cell, as the game does when content is withdrawn; the pentaxid tank is a crystal container, so its crystals are taken out of the tank block directly) |
| `POST /active` | token | form body `name` (own structure name, or `auto`), optional `player`: set the player's active structure (the one containers, find, transfers, inventory moves and crafting work from; default: aboard → last aboard in transfer range → nearest own in range); every item answer carries `workingFrom` (name, type, how, distance, note) |
| `POST /structure` | token | form body `name`, optional `player`: one of the player's (or faction's) own structures on the current playfield (exact, prefix, contains; closest first): type, size, power, shield, mass, pilot, tanks, distance, `dockedTo`, docked vessels, container count; never someone else's structure or a POI |
| `POST /system` | token | optional `system` (system name, or a body name for its `details`, default the current system; `known` = list of discovered systems), optional `player`: star class and planets, moons, gas giants with planet types and difficulty of a system the player or their faction discovered (any `DiscoveredPlayfields` row in it; `entered` = that body itself); `details` from the save's instanced template (`Templates/<playfield>/playfield.yaml`): description, special effects, gravity (g), atmosphere, oxygen, breathable (`AtmosphereBreathable`, missing = no), temperatures, radiation, resources |
| `POST /poi-trade` | token | form body `poi` (name or part), `detail` (1 = credits, only for POIs the player visited; no stock: not readable), `all` (1 = include everyday goods: food, ingredients, farming, deco/building blocks, market price < 1000), optional `player`: the POI's traders and the item names they sell and buy (TraderNPCConfig) grouped by price tier against the item's `MarketPrice` (below < 0.9, about ≤ 1.15, above ≤ 1.5, far above; `mf=` prices are factors of it), credits with `detail`; the POI is looked up among the POIs the player or their faction discovered (current playfield first), else by prefab display name as a general answer (`general`) |
| `POST /poi-terminal` | token | form body `poi` (name or part), optional `player`: the info terminal of a POI (dialogue tree from the scenario's `POI_*_Init` in Dialogues.ecf, English texts from Dialogues.csv, markup removed): terminal name and its screens with option labels; only for a POI within 2 km of the player or one they visited |
| `POST /quests` | token | form body `player`, optional `status` (`open` default = missions waiting or trades locked, `unlocked`, `all`), `near` (`playfield`, `system` or a distance in LY), `item` (name part), `max` (default 5): the player's trader missions from the scenario's `TD_*` dialogues (Dialogues.ecf) and the save's per-player-and-POI `DialogueVars` rows: factory, playfield, LY, faction, trader, status, what the open mission wants, reward, work-order price at a GIN, follow-up flag; closest first |
| `POST /mining-contracts` | token | form body: optional `ore` (name part), `faction` (name part): the scenario's mining contracts (`Eden_ContractMining_*` in Dialogues.ecf: token, faction, ores and amounts, credits, reputation), best paid first, at most 12, plus `rules` (cooldown seconds, the faction whose reputation gates the offers, the tier from which the faction can be chosen). With `mine=1` and `player`: all contracts plus `found` from the player's playfield: contract tokens in the inventory and containers in reach (`token`, `where`, `count`, `inventory`) and the contract ores there (`item`, `where`, `count`) With `advise=1` (implies `mine=1`): `advise: true`, `standings` (`faction`, `standing`, `tier` per contract faction, from game.dat) and `offer` (`faction`, `standing`, `tier`, `choiceTier`, `canChoose`: whether the refinery lets the player pick the faction). Contracts carry `weight`, their pick weight from LootGroups.ecf. With `mine=1` also `handIn` (the player's discovered POIs where contracts can be handed in, nearest first, at most 8: `where`, `ly`; prefabs whose NPC dialogues lead to the hand-in, a per-POI gate such as a mining vessel's own quest must be met), `gameTimeS` and `offers` (the player's refinery cooldown rows: `key`, `value` = next allowed game time, `where`). |
| `POST /cooldowns` | token | form body `player`: `gameTimeS`; `refineries` (refinery contract cooldown rows: `key`, `value` = next allowed game time, `where`, `ly` from the player's system; plus discovered POIs whose prefab hands out contracts but that have no row yet: `key` `poi:<id>`, `value` 0 = ready, `discovered: true`; the same rows in `/mining-contracts` `offers`); `missions`: repeatable PDA missions with a waiting time of 10+ minutes (from PDA.yaml `RepeatConditions`, hidden chapters left out) the player has done: `chapter`, `title`, `delayS`, `completedAt`/`readyAt` (recorded by the bridge from API1 PDA events into `VoxtaBridge.pdatimes.txt`; earlier runs unknown), `perPoi` (rows of the variable the completing dialogue sets to 1 per POI, value 1 = done there). |
| `POST /site-cargo` | token | form body `player`, `items` (`Item:count,…`): `needL` (the load's volume in litres, from the item config) and `space` = the harvest controllers on the player's ship and its docking group: `structure`, `harvestControllers`, `capacityL`, `usedL`, `freeL`. |
| `POST /quest-pursue` | token | form body `player`, `name` (factory name part, its playfield, or `none`): pursue one open trader mission; kept per player in `VoxtaBridge.pursued.txt` next to the DLL. `/status` then carries `pursuing.<steamId>` = `{status, factory, line, needs}` (`needs` = `[{item, name, count, tokenId?}]`, internal + display name, while open) (status `open`, `locked`, `done`, `gone`; refreshed at most every 10 s), and for every online player `missions.<steamId>` = open trader missions `[{key, kind, line, where, followUp?, pursued?, needs}]` (key = trader + mission number; kind `factory` when the trader's trades wait for the mission, else `trader`) for the new/completed-mission announcements (a key that leaves the list was handed in) |

`/status` also carries `chat.<steamId>` = the private messages the player sent to themselves (whisper to self) in the last 5 minutes `[{seq, channel, text, ageS, recipient}]` (IModApi `ChatMessageSent`; API1 `Event_ChatMessage` as fallback, the same message from both kept once; the bridge's own whispers are never taken in) and `chatSeq`; the module forwards new ones to the character.

`POST /chat-say` (token; form body `text`, `from` = sender name, optional `player`): a private message to the player in the game chat under that name (IModApi `SendChatMessage`, SinglePlayer channel), split into parts of at most 350 characters at sentence or line boundaries.

`/status` also carries `live.<steamId>` per online player: `{pos, posAgeS, boxesAgeS, visiting?, standing?, own[]}`. The playfield server's position of a player on foot lags up to a minute (seats are instant), so the dedi tests its fresh API1 position (asked every second) against the boxes of the structures near the player, sent by the playfield server with every snapshot (`VBL:` packets: world→block transform measured with `GlobalToStructPos` at three probe points). `visiting` = smallest structure that isn't the player's containing the position; `standing` = smallest own one within 3 blocks; `own` = own structures by distance. Missing when either part is older than 15 s.
| `GET /debug/pois/<playfield>` | token | every POI on a playfield with class, reason, turrets/sentries and whether anyone discovered it |
| `POST /marks` | token | form body `action` (`add`, `permanent`, `clear`, `list`), `stars` (comma separated), `numbered` (1 = route), `replace` (0 keeps earlier ones), optional `player`: Voxta's star markers on the galaxy map (private star bookmarks in `global.db` named `… (Voxta)`; rows are reused by moving/renaming; reached = `done: …`; deletions only when the player is offline); `permanent` with `star`, `name`, `hud` (0/1) writes a marker the player keeps (no suffix, never touched again; names ending in `(Voxta)` refused) |

Tanks in transfers: `to` / `from` may name a structure's tank, `Fuel Tank`, `Oxygen Tank`, `Pentaxid Tank` (`@ structure` when several are in scope). Only when named: never an implicit source, not listed by `/find` or `/containers`. As a target it takes the items its tank blocks accept (counted in items: content ÷ units per item); as a source it gives only the item the game withdraws (Fuel Cell, Oxygen Bottle, Refined Pentaxid). Not with `player` on the other side.

Transfer scope: the docking group of the structure the player is in (its carrier if docked, plus everything docked to the carrier), plus own structures within `TransferRangeMeters` (core to core) and their docking groups.

Config keys in `VoxtaBridge.cfg` (defaults): `TransfersEnabled=true`, `RequireOwnership=true` (structures must belong to the player or their faction), `MaxItemsPerTransfer=10000`, `TransferRangeMeters=1000` (0 = docking only), `PlayerVolumeLimit=1000` (litres; giving to a player stops there, 0 = no limit; the real capacity depends on armor/boosts, which the mod can't see).

Device control keys: `DeviceControlEnabled=true` (`/devices` write actions), `DevWriteTools=false` (development only: teleporter targets via `/devices`, and the write probe's command file `VoxtaBridge.probe.cmd.txt` next to the DLL). `signal`, `power`, `shield` and the shield details use game internals the mod API doesn't offer. They are only used on game builds the mod was checked against (SHA-256 of the playfield server's `Assembly-CSharp.dll`, list in `GameInternals.cs`); on any other build these actions answer with an error saying so, and everything else keeps working. `list` reports the check in `gameInternals` (`available`, `game`). `AllowUnverifiedGameInternals=false` (true = use them anyway; the methods are still found by shape and fail with an error rather than guess).

Micro jump keys: `MicroJumpEnabled=true`, `MicroJumpMinMeters=1000`, `MicroJumpMaxMeters=25000`, `MicroJumpCooldownSeconds=60`, `MicroJumpBodyClearanceMeters=2000` (aimed jumps at a planet or moon stop this far above its estimated surface; other targets: their size + 500 m), `MicroJumpHitLockSeconds=30` (no jump this long after the ship was hit: shield drop or block damage, sampled every second on the playfield server; 0 = off),
`MicroJumpRequireDrive=true`, `MicroJumpKmPerPentaxid=5` (cost = distance / this, rounded up, at least 1; paid with Refined
Pentaxid from the ship's pentaxid tank (crystals taken out of the tank block; needs the verified game build; refused if
the tank has too little; a refund goes back into the tank)). Keys missing from an existing cfg use these defaults.
